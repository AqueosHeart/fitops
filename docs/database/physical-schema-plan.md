# Issue #8: Physical schema and migration design

Status: revised design after the [first review](physical-schema-review.md), [second review](physical-schema-second-review.md), and [independent third pass](physical-schema-third-review.md). No Prisma schema, migration, or PostgreSQL race proof exists. [ADR 009](../adr/009-one-physical-session-row.md) records the physical mapping.

## Physical mapping and ownership

The [conceptual DBML](fitops.dbml) remains a product-level relationship map. The MVP uses **one physical `class_sessions` row** per public session. Scheduling's `SessionSlot` domain view maps program, trainer, start, and end from that row. Booking's `BookableSession` domain view maps the same immutable session identifier and interval plus capacity, cutoff, reservation status, and queue counter. The interval has one physical value; Booking receives a translated value object from its repository, never a Scheduling entity or adapter. Generated Prisma types stay inside infrastructure adapters. The database migration and Prisma schema become the executable source of truth only after implementation.

This mapping avoids a duplicated persisted snapshot while retaining [ADR 008](../adr/008-booking-owns-reservable-session.md)'s domain ownership. Administration coordinates Scheduling and Booking through one application transaction. Public discovery, trainer reads, booking cutoff, and overlap checks use the same `class_sessions.starts_at`/`ends_at` columns.

## Authentication and catalog choices

- MVP demo identities use email/password credentials. `users.password_hash` stores a salted, one-way password hash produced and verified by the Identity adapter; plaintext passwords and hashes never appear in seeds, logs, or API responses. Authentication uses Auth.js Credentials with JWT sessions and **no Auth.js database adapter/session/account/token tables**. Auth.js does not persist Credentials users for the application; FitOps creates them in its own registration transaction. [Credentials reference](https://authjs.dev/reference/core/providers/credentials); [session strategies](https://authjs.dev/concepts/session-strategies).
- A JWT contains only a stable user ID and `auth_version`. Every protected request reloads the User and relevant profile from PostgreSQL; role, active membership, and waiver state are never trusted from stale token claims. Incrementing `auth_version` invalidates previous tokens when an Identity security action requires it. The exact expiry, hashing algorithm, login throttling, and recovery behavior belong to Issue #9's security design before implementation.
- `/auth/forgot-password` currently has no contracted reset endpoint and the UX plan says recovery sends no email. No reset-token table or pretend delivery is included in Issue #8. If a real reset is approved later, update the canonical draw.io flow, API, threat model, and schema together before implementing it.
- The three fictional plan definitions (`base`, `complete`, `training_plus`), names, and publication flags live in one versioned application catalog. Both `GET /membership/plans` and registration validation read that catalog. `member_profiles.selected_plan_code` stores the chosen code; no payments, subscriptions, or catalog table are required in the MVP.
- Program publication is seed/configured catalog state in this MVP: no program-unpublish endpoint is contracted. Admin session creation requires a published program, and public session reads filter published programs. A future program-unpublish command must define its effect on already scheduled and booked sessions before it is added.
- Trainer specialties are a non-null `text[]` for display. No specialty filter is contracted. A normalized taxonomy table would require a later query need and migration.

## Field-level PostgreSQL design

All IDs are `uuid` primary keys generated by the application/seed. All instants are `timestamptz(3)`; the application sends UTC ISO 8601 values and selects a local timezone only for display. In the pinned Prisma version, every instant field must use its PostgreSQL native timezone-aware mapping (for example `@db.Timestamptz(3)`, rather than an unqualified `DateTime`). Required fields are `NOT NULL` unless marked nullable. `created_at`/`updated_at` are maintained by the application; database defaults may fill `created_at`, but the migration must match the pinned ORM contract.

| Table | Columns and types | Relationships / notes |
| --- | --- | --- |
| `users` | `id uuid`, `email varchar(320)`, `name varchar(120)`, `role user_role`, `password_hash text`, `auth_version integer DEFAULT 1`, `created_at timestamptz(3)`, `updated_at timestamptz(3)` | Unique normalized email. `role` controls staff routes; an owned MemberProfile controls member actions even for staff users. |
| `member_profiles` | `id uuid`, `user_id uuid`, `status member_status`, `selected_plan_code membership_plan_code NULL`, `plan_selected_at timestamptz(3) NULL`, `terms_privacy_accepted_at timestamptz(3) NULL`, `waiver_signed_at timestamptz(3) NULL`, `created_at timestamptz(3)` | Unique `user_id` FK to User. This row is the member reservation-calendar lock anchor. Nullable consent/plan fields allow earlier fictional demo personas; new registration validates all required values atomically. |
| `trainer_profiles` | `id uuid`, `user_id uuid`, `bio text`, `specialties text[] DEFAULT '{}'` | Unique `user_id` FK to User. Trainer row is the Scheduling lock anchor for assignment changes. |
| `programs` | `id uuid`, `slug varchar(100)`, `name varchar(120)`, `description text`, `intensity varchar(30)`, `duration_minutes integer`, `is_published boolean DEFAULT true` | Unique slug; only published programs appear publicly. |
| `class_sessions` | `id uuid`, `program_id uuid`, `trainer_id uuid`, `starts_at timestamptz(3)`, `ends_at timestamptz(3)`, `capacity integer`, `booking_cutoff_minutes integer`, `status session_status DEFAULT 'scheduled'`, `next_position_key bigint DEFAULT 1` | FKs to Program and TrainerProfile. The row is the Booking lock anchor. `booking_cutoff_minutes` is required on create; there is no hidden global cutoff default. A stored `completed`/`cancelled` status has no MVP mutation endpoint; future lifecycle operations need a new rule review. |
| `waitlist_entries` | `id uuid`, `member_id uuid`, `session_id uuid`, `status waitlist_status DEFAULT 'waiting'`, `position_key bigint`, `joined_at timestamptz(3)`, `resolved_at timestamptz(3) NULL` | FKs to MemberProfile and ClassSession. Resolved rows stay for history; positions are never renumbered. |
| `bookings` | `id uuid`, `member_id uuid`, `session_id uuid`, `status booking_status DEFAULT 'confirmed'`, `booked_at timestamptz(3)`, `cancelled_at timestamptz(3) NULL`, `source_waitlist_entry_id uuid NULL` | FKs to MemberProfile and ClassSession. Promoted bookings reference the source waitlist entry; direct bookings have NULL. `booked_at` means confirmation time, including promotion time. Cancelled rows stay for owner-safe repeated DELETE. |

No separate `member_reservation_calendars` table is needed: the member row lock plus the member's confirmed bookings represent the domain aggregate's intervals. The schema has no payment, billing, health-answer, PAR-Q, real-customer, or real-subscription data.

## SQL constraints and indexes to review in the first migration

These are required database properties, regardless of whether the pinned Prisma version can express each in its schema language. The reviewed migration SQL must contain any unsupported constraint. Use real PostgreSQL foreign keys (`relationMode = foreignKeys` or equivalent for the pinned version), never ORM-only emulation.

1. **Identity and references.** `users.email` is stored as `lower(btrim(email))`; add `CHECK (email = lower(btrim(email)))` and `UNIQUE (email)`. Check `auth_version >= 1`. All FKs are non-null except the optional promotion source. Use explicit `ON DELETE RESTRICT` and `ON UPDATE NO ACTION` for User/Profile, Program/Session, Trainer/Session, Session/Participation, Member/Participation, and promotion-source relationships. Demo reset is an explicit controlled operation, not an implicit cascade.
2. **Valid values.** Check `programs.duration_minutes > 0`, `class_sessions.starts_at < ends_at`, `capacity > 0`, `booking_cutoff_minutes >= 0`, `next_position_key >= 1`, and `waitlist_entries.position_key > 0`. Pair `selected_plan_code` with `plan_selected_at` when one is present. New registration still enforces required consent/plan fields in its transaction; nullable legacy demo fields are not a bypass of booking eligibility.
3. **State and time.** Confirmed bookings have `cancelled_at IS NULL`; cancelled bookings have non-null `cancelled_at >= booked_at`. Waiting entries have `resolved_at IS NULL`; promoted/cancelled/expired entries have `resolved_at >= joined_at`. `booked_at` and `joined_at` use the database wall clock within their transaction. Enum values and status transitions are checked by the domain use cases; no endpoint may set future-only session statuses in MVP.
4. **Active uniqueness.** Unique partial indexes on `bookings(member_id, session_id) WHERE status = 'confirmed'` and `waitlist_entries(member_id, session_id) WHERE status = 'waiting'`. Add unique `(session_id, position_key)`. Add `UNIQUE (source_waitlist_entry_id)` for non-null promotion sources. To prevent a link to another member/session, add `UNIQUE (id, member_id, session_id)` on waitlist entries and composite FK `(source_waitlist_entry_id, member_id, session_id)` from bookings to those columns. The application additionally requires the source entry to be `promoted` in the same transaction.
5. **Trainer interval.** Add `btree_gist` and an `EXCLUDE USING gist` constraint on `(trainer_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)`. Adjacent sessions may touch at the endpoint. The constraint covers all persisted sessions in the MVP. The application still locks affected trainer rows in sorted UUID order, checks overlap after locks, and maps a constraint violation to a stable conflict response. [PostgreSQL range constraints](https://www.postgresql.org/docs/current/rangetypes.html).
6. **Read indexes.** At minimum: `class_sessions(starts_at, status)`, `(program_id, starts_at)`, `(trainer_id, starts_at)`; `bookings(session_id, status)` and `(member_id, status, session_id)`; `waitlist_entries(session_id, status, position_key)` and `(member_id, session_id)`. Verify actual query plans before adding overlapping indexes. The trainer exclusion index does not automatically replace every ordered list index.

The two partial unique indexes cannot enforce **one active participation across two tables**. That business invariant is mandatory and uses the transaction protocol below. Capacity and member overlap also need transactions. A database trigger or unified participation table is deferred because it adds a second implementation path; revisit if the locked protocol cannot be proven or if future writers cannot follow it.

## Required transaction and transition contract

Use PostgreSQL `READ COMMITTED` with a whole-transaction retry only for deadlock/serialization failures, bounded by a small configured retry count. No error path commits partial state. After locks, read `clock_timestamp()` for a strict `clock < starts_at - booking_cutoff_minutes` test. PostgreSQL `now()` is fixed at transaction start and is unsuitable after a lock wait. Recheck time after candidate member locks in either promotion scan per [ADR 011](../adr/011-recheck-cutoff-during-cancellation-promotion.md) and ADR 010. Re-read every relevant row/count under the locks. Do not derive authoritative state from client values.

| Command | Locks in order | Required checks and atomic result |
| --- | --- | --- |
| Register | Unique normalized-email insert within one transaction | Create User, MemberProfile, plan selection, and required consent timestamps together. A duplicate email or invalid catalog code leaves no partial account. |
| Admin create | Target TrainerProfile, then new ClassSession | Validate published program, trainer, time, cutoff, positive capacity, and no trainer overlap. Insert one row; exclusion constraint backstops the overlap check. |
| Admin edit | Affected TrainerProfile rows sorted by UUID when scheduling fields can change, then ClassSession, then promoted candidates' MemberProfile rows | Re-read the session after locking it; if its current trainer differs from the trainer used to choose locks, restart the whole transaction with the correct trainer set. Check **any historical** booking or waitlist row. If none, allow documented program/trainer/time/cutoff/capacity edits with overlap and validity checks. If any exists, permit capacity only, and require `confirmed_count <= new_capacity`. On an increase before cutoff, expire ineligible waiters and promote eligible waiters in FIFO order until free seats or waiters run out, in the same transaction. Recheck the database-clock cutoff after each candidate member lock and abort the whole increase if it passes before a promotion. Reject an increase after cutoff while waiting entries remain. Return final counts. Never silently change status or cancel participants. [ADR 010](../adr/010-promote-waitlist-on-capacity-increase.md). |
| Book | ClassSession, then MemberProfile | Recheck owned active membership, waiver, scheduled state, database-clock cutoff, no confirmed or waiting entry for this member/session, no overlapping confirmed session, and `confirmed_count < capacity`. If any waiting entry coexists with a free seat, return `500 PARTICIPATION_INVARIANT_BROKEN` with a generic response, raise an operational alert, and require explicit repair; never leapfrog. Insert one confirmed booking. Fullness returns `SESSION_FULL` and lets the member choose the separate waitlist action. |
| Join waitlist | ClassSession, then MemberProfile | Recheck eligibility, status/cutoff, no confirmed or waiting participation, and full capacity. If a seat is open while any waiting entry exists, return the same `500 PARTICIPATION_INVARIANT_BROKEN` response and alert as direct booking. If a seat is open and no one waits, return `SEAT_AVAILABLE` without inserting. Assign `position_key = next_position_key`, increment the counter, insert waiting entry in one transaction. Rollback restores both counter and entry. |
| Cancel confirmed booking | ClassSession, then each candidate MemberProfile in FIFO scan | Re-read owner and current status. If already cancelled, return `204` to that owner without cutoff evaluation or another promotion. If confirmed, check cutoff, then cancel it. For each waiting entry by `position_key`, lock the candidate member, recheck the database-clock cutoff, then recheck eligibility and overlap; abort and roll back the entire cancellation if cutoff passed during a lock wait. Otherwise expire ineligible entries, or mark the first eligible entry promoted and insert its linked confirmed booking. Commit cancellation, expiries, and promotion together. |
| Leave waitlist | ClassSession, then target MemberProfile | Re-read owner and waiting status. Mark waiting entry cancelled. If already promoted, return the conflict and leave its booking untouched. Repeated removal of an already-cancelled owned entry has no second effect. |
| Update membership/waiver | MemberProfile | These writes serialize on the same member row. Booking/promotion rechecks after obtaining that row; a later deactivation does not retroactively delete a committed booking. |

The status transition graph is `waiting -> promoted | cancelled | expired` for a waitlist entry and `confirmed -> cancelled` for a booking. Promotion is a two-record transition: update waiting entry to promoted and insert exactly one linked confirmed booking. `promoted` entries are no longer waiting. A member may later create a new participation after cancelling/leaving; the old rows stay as history. The queued member is **not** pre-checked for time overlap when joining; promotion checks current overlap, as the API requires. The public displayed position is computed from current waiting rows and is only a snapshot.

Registration commits a complete User and MemberProfile before issuing an Auth.js cookie. If cookie issuance then fails, the completed account remains valid and the response must direct the visitor to retry login; a retry of registration must not create a second account. This is an authentication-delivery failure, not a partial database enrollment.

Every writer of participation or capacity uses the same ClassSession lock. Commands that may confirm a member also take that MemberProfile lock before overlap checks. Admin schedule edits take trainer lock(s) before the ClassSession lock; booking commands never take a trainer lock, so the graph has no trainer/session inversion. A schedule edit must revalidate its initial trainer read after the session lock, since another edit can change the assignment while it waits. Promotions on different sessions can still deadlock while locking members; retry the **entire** transaction. Issue #7's seven interleavings remain the base acceptance matrix; [ADR 010](../adr/010-promote-waitlist-on-capacity-increase.md) adds capacity-increase races and rollback cases.

## Migration and proof sequence

1. Pin PostgreSQL, Prisma, Auth.js, and Node versions in the implementation change. Verify native type and partial-index syntax for those versions. Do not mix Prisma migration formats across major versions.
2. Author `prisma/schema.prisma` with exact field/relation mappings and named indexes. Generate the first migration in review mode, inspect its SQL, add any needed PostgreSQL checks/partial indexes/exclusion/composite FK using the pinned migration mechanism, and commit schema plus every migration together.
3. Apply migrations to a fresh disposable PostgreSQL database, then recreate it and apply again. Inspect migration status and schema drift. Test rejected inserts/updates for each check, unique index, FK, and trainer exclusion rule; verify fictional seed recreation and no plaintext credential or real-person data.
4. Implement repository ports and the shared transaction coordinator. Run synchronized PostgreSQL tests for Issue #7's seven race scenarios and both winner orders where relevant. Add tests for confirmed-plus-waiting attempts, promotion provenance, rollback during promotion, history-based edit freeze, trainer reassignment while the editor waits for locks, trainer overlap, and waiting across the cutoff lock. Include cancellation and capacity increase versus booking/cancellation, multiple new seats, an ineligible first waiter, cutoff crossing during either promotion scan, and failure after one capacity-increase promotion. Sequential unit tests do not prove race safety.
5. Keep Issue #8 open until the Sprint 0 review and Sprint 1 low-fidelity design gate permit implementation, and the executable schema, committed migrations, constraints, and race tests pass. This document is design evidence only.

## Design limits still tracked

- Issue #9 must settle password hashing parameters, login throttling, JWT lifetime and revocation, and the demo recovery screen. The schema reserves `password_hash` and `auth_version` without claiming those controls are implemented.
- Cancellation/deletion of a class session, participant migration, real payment enrollment, and real email reset are outside MVP scope. Any such change requires requirements/API/UX and schema review.
